## Session behaviour (observed on the binary, asserted by the smoke test)

| Event | Existing token of the managed superuser afterwards |
| --- | --- |
| Plain restart, no upsert (upstream alone) | still valid |
| Password changed over the API (`PATCH` on the record) | refused (403) at once, without a restart |
| Restart with `superuser upsert` and a new password | refused |
| Restart with `superuser upsert` and the **same** password | refused |
| `superuser upsert` on the same password while the server is running | refused at once |
| Restart with `superuser upsert` of the managed account: another superuser's token | still valid |

So: **a password change signs out that account's sessions, and so does every
restart of this template**, because the upsert re-saves the record and
PocketBase rotates the record's token key whenever a password is set, changed
or not. Other superusers and app users are unaffected. Stated in the README
and asserted by four smoke cases (plain restart, rotation, change inside
PocketBase, a hand-made superuser's session surviving the managed upsert).

The interrupted-start rows measure the kill delay and assert the outcome. As
an observation, not an assertion: at 0.15 s the killed run's log had no
`Server started` line yet (the kill landed during the bootstrap), at 0.5 s
and 1.0 s it had.

Measurements from the same run:

* **Peak memory during the 50-record case at 256 MB:** 10.0 MiB by
  `docker stats` (2 samples; each call takes about two seconds), 11 MiB by
  sampling the cgroup's `memory.current` at 10 Hz (26 samples), 14 MiB
  `memory.peak` for the whole run of that process up to that point (start,
  migrations, first requests). Earlier runs of the day gave 9.8 to 11.5,
  11 to 12 and 14 to 16 MiB. Not a pass/fail; recorded for sizing.
* **Disk full, what was actually tested:** App storage was a 3 MB tmpfs
  mounted with `uid=0,gid=1001,mode=2770`, the same ownership shape as the
  platform's mount, and the app ran as 1001:1001. 115 records of about 5 KB
  filled it (`df` showed 3.0M of 3.0M). The 116th create returned a JSON 400
  with the generic message `Failed to create record.`; the underlying
  "disk is full" reason is not exposed to the client and PocketBase prints
  nothing to the console for it. Health stayed 200 and the process did not
  exit. Deleting records over the API while full: 1 of 3 deletes succeeded
  and a small create afterwards still failed, so freeing space from inside
  the app is not reliable once the disk is at 100% (SQLite cannot checkpoint
  its write-ahead log into the main file). The reliable recovery is more
  space: the files were copied out of the running container with tar (tmpfs
  cannot be copied with `docker cp`) onto a larger mount, and the app came up
  healthy there with all 115 records and accepted writes. That is the
  equivalent of growing App storage.
* **SIGKILL mid-write:** the kill landed after 20 acknowledged creates; after
  restart all 20 were present and the total was consistent.
* **Review fixes, verified with the old image side by side:** the image built
  from the first commit exits 1 with `unknown flag: --<value>` for a password
  starting with `--`, printing the value; the fixed image starts and the
  password logs in. The `--help`/`-h`/`--version` quirk above is the only
  dash-prefixed input left that cannot be a password.

## Not verified here

* Anything that needs the platform: the deploy link, the form, secret
  binding, the edge, HTTPS, custom domains, automatic rollback, realtime
  through the edge, App storage growth. See the next section.
* A hook doing real work. The smoke test proves a hook file in the image's
  `pb_hooks` runs and the same file on App storage does not; the hook only
  prints a line.
* Build on the platform's builder and its time budget. The local build takes
  a few seconds plus the 12 MB download.
